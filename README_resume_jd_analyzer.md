# 简历-JD 契合度分析器:一个用链式调用 + 防幻觉设计的 LLM 评估工具

## 解决的问题

求职者对照 JD 逐条检查自己的简历,是一件枯燥且容易出错的事:条目多、
措辞不统一、容易漏看,也容易因为主观印象而高估或低估自己的匹配度。让
LLM 直接读一遍 JD 和简历、给一个"匹配度"或"建议",看似是最省事的做
法,但这样做会遇到两个实际问题:一是判断过程不透明,你不知道模型说
"部分符合"到底是根据简历里的哪句话下的结论;二是模型在被要求"给出具
体建议"时,倾向于把建议写得越具体越好,而"具体"往往是靠编造简历里不
存在的项目经历、数据指标堆出来的。

这个项目要解决的核心问题不是"怎么调用 LLM 做比对",而是**怎么让 LLM
的评估输出变得可信、可核查**。做法是把一次性的"读 JD、读简历、给结
论"拆成五个职责单一的环节,每一环只做一件事,上一环的输出是下一环的
输入,关键判断都要求先摘录证据再下结论,并且用一个独立的环节反过来审
查前面环节的输出。

## 核心设计:五环链式架构

### 环1(LLM):从 JD 提取结构化要求条目

这一环只做一件事:把 JD 的自然语言正文,转成一个 JSON 数组,每条要求
标注 `requirement` 文本和 `type`(`hard`/`soft`)。之所以在链条的第一
步就强制输出结构化 JSON,而不是让模型直接输出一段"要求总结"的文字,
是因为后面每一环都需要用代码去确定性地解析和遍历这份要求列表——环2
要逐条比对,环3 要逐条统计,环4 要逐条生成建议。自然语言总结对人可读,
但对代码不可靠:条目数量、边界、格式都可能因模型的措辞习惯而漂移。只
有先把"要求"这个概念固化成一个可以用 `json.loads` 解析的数组,后面的
环节才能建立在一个稳定的数据结构上,而不是每一环都要重新做一次自然语
言理解。

### 环2(LLM,CoT + 引用原句):逐条语义比对

这是整个链条里对"可信度"最关键的一环。对 JD 的每一条要求,模型要输出
四个字段:`requirement`、`evidence`(简历中支撑判断的原句,找不到则为
空字符串)、`verdict`(met/partial/missing)、`reason`。System prompt
明确要求模型必须先在简历原文里定位证据,再根据证据下判定——不允许在
没有简历依据的情况下把"感觉应该会"当成"met"。这里做了两件事:第一,
`evidence` 字段的存在本身就是一种可验证性设计,任何人拿到这份 JSON 都
可以逐条核对模型的判断是否真的能在简历原文里找到对应的句子,而不是只
能选择相信模型的一面之词;第二,要求模型"先摘证据、再下判定"这个顺序
本身就是一种简化版的思维链(CoT)约束,把"证据"设计成判定的前置条件,
而不是判定完了再补一个理由,能有效减少模型跳过论证直接下结论的情况。

### 环3(纯 Python,不调用 LLM):归类统计

拿到环2 的 JSON 之后,按 `verdict` 分成 met / partial / missing 三组,
分别计数,再算一个粗略契合度(met 数 / 要求总数)。这一步刻意不再调用
LLM,因为分类计数是一个纯粹的确定性计算,Python 的 `dict` 和除法运算
不会算错,而如果把这一步也交给 LLM,反而可能因为模型的计数或算术错误
引入新的不确定性——这类问题应该用最简单、最可验证的工具解决,而不是
"能用 LLM 就用 LLM"。作为附带好处,这一环完全不消耗 token,也不产生
调用成本。

### 环4(LLM):生成改进建议,并加入防编造硬约束

针对 partial 和 missing 的条目,生成中文、语气礼貌鼓励的具体改进建
议。这一环是链条里幻觉风险最高的一环:因为 system prompt 明确要求"给
出具体、可执行的建议",模型为了满足"具体"这个指标,会倾向于主动补充
简历里没有出现过的细节——比如编一个"与5个部门访谈"这样的场景,让建
议看起来更扎实。单纯要求"不要编造"效果有限,因为模型没有一个"诚实说
不知道"的默认选项,它更倾向于把要求填满。因此在 system prompt 里加了
一条明确的硬约束:如果某条要求在简历中缺乏任何可利用的基础,就直接说
"简历中暂无相关基础,建议从零积累",而不是编造细节。这条约束的作用本
质上是给模型一个"诚实退出"的通道——与其逼着模型在"没有素材"和"编造
素材"之间二选一,不如明确告诉它"承认没有"也是一个合法答案。

### 环5(LLM,输出检查):质检环4的建议

把环4 生成的建议连同环2 的逐条比对结果一起交给模型,让它以质检员的身
份重新审查:每条建议是否基于简历中真实存在的信息(对照环2 的
`evidence` 字段核实),以及是否具体可落地而不是空话。发现问题就标记
并说明原因,不负责自动重写。这一环之所以有效,原因有两点:第一,它是
一次独立的 LLM 调用,不共享环4 生成建议时的上下文和"生成压力",单纯
站在审查者的角度看待已经写好的文本,更容易发现问题;第二,它依靠的是
环2 留下的原句证据做核对基准,而不是重新读一遍简历去"印象式"判断,所
以哪怕环4 的编造写得非常自然、非常像真的,只要环2 的证据里找不到对应
支撑,环5 就能识别出来——它不会被环4 的幻觉"传染",因为核对的标尺是
环2 的证据,不是环4 的措辞。

## 关键工程决策

### 防幻觉的多层设计

这个项目里"防止编造"不是靠一句 prompt 指令解决的,而是叠了三层:环2
的原句引用(让判断本身可追溯)、环4 的硬约束(给模型一个诚实退出的选
项)、环5 的独立质检(用环2 的证据反过来审查环4 的输出)。之所以做成
多层而不是指望某一层单独解决问题,是因为实测发现单层并不够:给环4 加
上硬约束之后,编造的情况明显减少了(比如缺乏 Python 经验的条目,模型
会老实写"简历中暂无相关基础"),但并没有完全消失——在真实数据的一次
运行中,环4 仍然给一条"处理模糊需求"的建议编造了"与5个部门的需求访
谈"这种简历中并不存在的细节。这说明"要求模型不要编造"这件事本身不可
能靠一条指令做到 100% 可靠,所以必须留一道独立的复核环节兜底,而不是
信任某一次调用的自觉性。

### 防御性解析(`_strip_code_fence`)

环1 和环2 的 system prompt 都明确要求"只输出 JSON,不要 markdown 代码
块",但实测中 Haiku 仍然会时不时把 JSON 包一层 ` ```json ... ``` `
再输出。这不是 prompt 写得不够清楚,而是模型在这类指令上并非 100% 稳
定遵循。与其反复调整措辞去赌下一次会不会听话,不如在解析层加一步防御
性处理:先尝试剥离首尾的代码块围栏,再交给 `json.loads`。这样即使模型
偶尔"违反"格式指令,也不会导致整条链路因为一个可预期的、容易修复的
偏差而直接崩溃;真正解析失败(比如输出被截断、字段缺失)时,仍然会打
印模型原始输出并退出,保留排查线索。

## 运行示例

以下片段来自一次真实 JD(某 AI 产品团队的模型评估 PM 岗位)与真实简历
的运行结果,展示环5 抓出环4 编造内容的过程。

环2 对"处理模糊需求的能力"这条要求给出的证据和判定:

```json
{
  "requirement": "Ability to handle ambiguous requirements",
  "verdict": "partial",
  "evidence": "Established an analytical framework by collaborating with stakeholders from product, marketing, content operations, and strategy teams to gather requirements",
  "reason": "Resume shows stakeholder collaboration and requirement gathering but does not explicitly address handling ambiguous requirements."
}
```

环4 针对这条要求生成的建议里,补充了一个简历中并不存在的具体场景:

> 如果可能，补充一个具体案例：例如"某个数据项目初期目标模糊，通过与
> **5个部门的需求访谈**，最终确定了核心指标体系"

环5 质检时,回头核对环2 的 `evidence` 字段,发现这条"5个部门访谈"完
全找不到依据,于是明确标记为编造:

> ❌ **建议4：处理模糊需求能力 - 编造具体数据**
> 证据链断裂：比对结果中仅有 "Established an analytical framework by
> collaborating with stakeholders"，完全没有关于"需求变更率"、"5个
> 部门访谈"等具体数据的 evidence。这是明确的编造。
> 建议：删除所有量化数据（"5个部门"、"需求变更率"）。仅保留可验证的
> 部分。

环4 单独看是一条"写得很像真的"的建议,但环5 依靠环2 留下的证据链,准
确定位了具体是哪句话、哪个数字没有依据——这正是五环架构要达成的效
果:不依赖某一次 LLM 调用足够诚实,而是让链路本身具备核查能力。
